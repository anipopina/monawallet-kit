# MonaWallet Kit 設計メモ

実装上の判断と、運用上の制約をまとめる。数値や既定値はコードの定義（主に [`src/core/constants.ts`](../src/core/constants.ts)）を正とする。

## 鍵導出（変更禁止）

- PRFのsalt：`SHA-256("wallet-seed:v1")`
- PRF出力（256bit）→ BIP39英語24単語（パスフレーズなし）→ `m/44'/22'/0'/0/0` → P2PKH（`M`で始まるアドレス）
- この仕様で作成済みのウォレットがあるため、変更するとそれらにアクセスできなくなる。結果はテストベクトル（[`src/core/__tests__/vectors.ts`](../src/core/__tests__/vectors.ts)）で固定している。
- P2WPKHはサポートしない。Monacoinでは取引所の対応状況が悪く、トラブルの原因になりうるため。

## RP ID

- PRFの出力はPasskeyに、PasskeyはRP IDに紐づくため、RP IDが変わると別のウォレットになる。このため `rpId` は利用側の必須設定にした。すでにウォレットを発行しているサービスに導入するときは、それまでと同じRP IDを指定する。
- 「ホスト名の末尾2ラベル」のような自動算出は、`co.jp` や `github.io` などで誤るため行わない。
- サービスごとにオリジンとRP IDが異なるため、ウォレットはサービス間で共有されない（要件としない）。
- 開発時は `localhost` か、`tailscale serve` によるHTTPS（`*.ts.net`）で開く。WebAuthnは安全なコンテキスト（HTTPS または localhost）を必要とし、IPアドレスはRP IDにできない。開発用のRP IDで作ったウォレットは本番とは別物になる。

## Passkey

- 登録時に `residentKey: 'required'` を指定する。再接続は `allowCredentials` なしで資格情報を選ばせるため、発見不能な資格情報が作られると二度と開けなくなる。
- PRFの対応判定は `PublicKeyCredential.getClientCapabilities()` がある環境でのみ確定できる。それ以外は `unknown` を返し、非対応は接続時に `prf_unsupported` として判明する。PRF非対応の環境に代替の鍵生成は提供しない。
- 登録のたびに別の資格情報、つまり別のウォレットができる。複数のPasskeyを同じウォレットに関連付ける仕組みは持たない。UIでは既存のPasskeyで開く操作を主にし、新規作成すると別のウォレットになることを明示している。
- パスワードマネージャー拡張（1Passwordで確認）は `navigator.credentials` を置き換え、拡張側の実行環境（realm）で作った ArrayBuffer をPRF出力として返す。この値は `instanceof ArrayBuffer` が false になるため、WebAuthn の戻り値を `instanceof` で判定しないこと（`ArrayBuffer.isView()` などを使う）。
- 登録と接続はそれぞれPasskeyの操作が必要で、新規作成時は2回になる。登録時にPRFを評価して1回にまとめる方法は、認証器によって対応状況に差があるため見送った。

## 状態と秘密情報

- 状態は `disconnected` / `readonly` / `unlocked` の3つ。readonly は残高の表示だけができ、署名・送金・ニーモニックの表示には unlocked（Passkeyによる解除）が必要。
- PRF出力、秘密鍵、エントロピーは `#private` フィールドにだけ保持し、ロック・切断時に0で埋めて破棄する。ニーモニックは保持せず、`revealMnemonic()` のたびにエントロピーから生成する。
- Vueの `ref()` などに入れても Proxy 化されないよう、`MonaWallet` に `__v_skip` を付けている（Proxy経由では `#private` フィールドにアクセスできないため）。UIには秘密情報を含まないスナップショット（`getSnapshot()` / `subscribe()`）だけを渡す。
- ライブラリは何も永続化しない。readonly 状態での再表示用にアドレスを保存するかどうかはアプリが決める（デモでは localStorage に保存している）。
- バックアップ（ニーモニックの表示）は任意で、利用開始の条件にしない。

## 残高・UTXO

- 送金直後は、API結果に自分の送金をローカルで重ね合わせる（使用済みの入力を除外し、お釣りを未承認として追加する）。お釣りは署名済みトランザクション全体を保持しているため、APIに反映される前でも次の送金の入力に使える。
- この情報はメモリ上にしかなく、再読み込みすると失われる。直後にAPIがまだ使用済みのUTXOを返すと、それを使った送金はノードに二重支払いとして拒否される（`broadcast_failed`）。
- 未承認のUTXOも送金に使う（`spendUnconfirmed` で変更可）。ただしコイン選択では承認済みのものを優先する。
- 残高更新が同時に呼ばれた場合は、実行中の取得結果を共有する。`maxAgeMs` を指定したときだけキャッシュを返す。

## チェーンAPI

- 既定：Esplora（electrum-mona）を使い、通信障害時は Monaparty（counterblock、2エンドポイント）にフォールバックする。障害が起きたプロバイダーは60秒間後回しにする。
- Monapartyの `get_chain_address_info` はmempoolを反映しない。フォールバック中は `balance.includesMempool = false` になり、UIは未承認の入出金が反映されていない可能性を表示する。
- ブロードキャストへの4xxはノードによる拒否とみなし、別経路で再送しない。
- `ChainProvider` を実装すれば、別のAPIに差し替えられる。

## 送金

- 金額は sat の整数で扱う。入力は10進文字列として厳密に解析し、浮動小数点の掛け算はしない（`0.29 * 1e8` は 28999999.99… になる）。
- コイン選択は、入力を追加するたびに手数料込みで判定する。入力が多いほど手数料が増えるため、選択を終えてから手数料を足すと不足することがある。手数料は P2PKH の概算 vsize と既定の手数料率から計算する。
- 546 sat 以下のお釣りは出力にせず、手数料に含める。確認画面に出す `feeSat` はこれを含んだ実額。
- `prepareSend()` で送金内容（宛先・金額・手数料・お釣り）を確定し、利用者が承認したら `send(plan)` で署名・送信する。plan は1回しか使えず、内部のトランザクションはアプリから改変できない。入力が使用済みなら `stale_plan` になる。
- `maxSendSat` で1回の送金額に上限を設定できる。デモでは 0.01 MONA に設定している。

## メッセージ署名・認証

- 署名形式はBitcoin互換（プレフィックスは `\x19Monacoin Signed Message:\n`、署名は base64 の65バイト）で、Monacoin Core の `signmessage` / `verifymessage` と同じ形式。`@noble/curves` で実装しており、Buffer ポリフィルは要らない。
- サインイン用のメッセージはSIWE風。サービス名、オリジン、nonce、発行日時、有効期限を含む。
- クライアントの `signInChallenge()` は、オリジン・アドレス・有効期限が一致しなければ署名しない。一般用の `signMessage()` はサインイン形式のメッセージを拒否し、取り違えを防ぐ。
- サーバー（`monawallet-kit/server`）は形式、サービス名、オリジン（開発用に複数可）、有効期限、署名を検証する。最後にアプリの `consumeNonce` を呼ぶ。nonceの保存・原子的な使用済み化、セッション発行、ユーザー情報はアプリの責務。
- これはウォレット鍵の署名による認証で、PasskeyのWebAuthn認証（PRFの取得）とは別物。

## UI

- Vue 3専用。`<dialog>` を使ったモーダルで、狭い画面では下からのシートとして表示する。通知ライブラリには依存せず、結果やエラーはモーダル内に表示する。アプリは `sent` イベントで自前の通知を出せる。
- 色などは `.mwk-root` 上の `--mwk-*` トークンで定義しており、アプリから上書きできる。QRコードは読み取りやすさを優先し、常に白地に黒で描く。アイコンは本ライブラリ用に描いた簡易なSVG。
- 送金完了画面には、ブロックエクスプローラーでトランザクションを開くリンクを出す。既定は `DEFAULT_EXPLORER_TX_URL`（electrum-mona のEsplora）で、モーダルの `explorerTxUrl` で変更・非表示にできる。
- アドレスを8色（常に `M` である先頭を除いた16文字を2文字ずつ）で表す配色をモーダル下端のフチに表示する。デザイン用途だが、アドレスの取り違えに気づきやすくなる効果もある。アプリでも同じ配色を使えるよう `addressColors()` と `AddressColors` を公開している。同じアドレスが同じ色になるよう、アルゴリズムはテストで固定している。帯はモーダル下端の右寄り（幅40%、右は角丸の分だけ離す）に置く。ライトモード（`prefers-color-scheme: light`）では暗く見えるため `filter: contrast(50%) saturate(300%)` をかける（配色の値自体は変えない。アプリ独自のカラーモードでは利用側で `filter` を上書きする）。
- 文言は日本語のみ。エラーはコードから文言に変換して表示し、例外の内容は表示しない。分類できない例外はコンソールにだけ出力する。
